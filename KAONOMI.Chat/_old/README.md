# KAONOMI.Chat

Avalonia desktop client for Kaonomi: chat with the local server/Ollama pipeline, follow a scrolling news ticker, export conversations to JSON or Word, manage cache and symbolic-pattern documents, and run a small HTTP JSON client.

## Run

```bash
dotnet run --project KAONOMI.Chat
```

Requires the Kaonomi server (and Ollama / Elasticsearch as configured by the server).

## Configuration

Files are copied next to the executable on build.

### `config.yml`

| `tts.robot` | Robotic effect on the voice reading the answers: `0` = natural (default), `0.3` = slight, `1` = plainly robotic. Each WAV from Piper gets a ring modulation (the voice multiplied by a 55 Hz sine, mixed with the voice) and a comb filter (7 ms delay with feedback, a metallic resonance) before it is played; combined with `tts.pitch` and `tts.speed` |
| `tts.vibrato` | Vibrato of the voice reading the answers: `0` = steady (default), `1` = a singing vibrato. Each WAV from Piper is read through a delay swinging at 5.5 Hz (heard rate, kept whatever `tts.pitch`), which makes the pitch waver by up to ±4.5 % (about ±0.8 semitone), with a slight tremolo at the same rate; applied after `tts.robot` and before `tts.pitch` |
| `tts.assistant` | Sheen of an AI assistant on the voice, like the AI of a film heard through the speakers of a high-tech room: `0` = dry voice (default), `1` = full. ### Paths on Windows, macOS and Linux

At each start, the chat brings the paths of `config.yml` to the standards of the system it runs on, so the same files work after moving from one system to another. A path written on another system (a drive letter or backslashes on macOS / Linux, `/Users/…` or `/home/…` on Windows, `/home/…` on macOS, `/Users/…` on Linux, `~/…` anywhere) is mapped to the same place here:

- **Home folder**: `C:\Users\jerome\kaonomi\promptscollection` ↔ `/Users/jerome/kaonomi/promptscollection` ↔ `/home/jerome/kaonomi/promptscollection`.
- **Standard folders**: Music, Pictures, Documents, Desktop, Videos / Movies and Downloads become the ones of this system (also when they were under OneDrive on Windows), e.g. `C:\Users\jerome\OneDrive\Pictures\kaonomi\maths` → `~/Pictures/kaonomi/maths`.
- **Piper**: `venv/bin/piper` (macOS, Linux) ↔ `venv\Scripts\piper.exe` (Windows).

These paths are adapted: `json.resultDirectory`, `json.collectionDirectory`, `prompts.directory`, `regexAssistant.directory`, `tts.voicesDirectory`, `tts.piper`, the voices of `tts.voices` given as `.onnx` paths, `pictures.directory`, `music.directory` and `calculator.graphDirectory`. The new value is written into `config.yml` (only that line; comments and the other lines are kept) and listed in the activity log (`Settings`). A path outside the home folder (another drive, a system folder) goes to its usual place: `~/kaonomi/<folder>` for the data folders (created), the Pictures / Music folder of the system for the libraries, the default folder for the calculator graphs; the Piper path is then left as it is (the usual places are searched). A data folder written for this system but missing is created in `~/kaonomi` as before. The picture links of the calculator tape (`calculator-tape.txt`, `![graph](path)`) are adapted the same way.

## Chat slash commands

A prompt starting with `/` is always handled locally and **never sent to the completion service** (`POST /aiassistant`): either it is one of the commands below, or the chat answers `unsupported command!` (e.g. `/foo`, `/theme:unknown`). Only prompts that do not start with `/` are sent to the model.

| Command | Opens |
| --- | --- |
| `/cache` | Cache search / edit window |
| `/json` | Mini HTTP JSON client |
| `/symbol` | Symbolic pattern search / edit window (several regex patterns per document, each checked as it is typed, and a **Regex assistant**: type example lines and the extraction goal, **Generate regex** asks the local Ollama model selected in the chat window directly (`POST /api/chat`, JSON output `{"regex": …}`; the Kaonomi `/aiassistant` pipeline is not used), only the regex is kept from the answer, tested on the examples (✓/✗ with the named groups) and can be edited; **Add** appends it to the regex patterns of the selected document; **Save…** stores the regex with its goal and examples as JSON in `regexAssistant.directory`, **Load…** brings them back) |
| `/ontology` | Ontology management window (node tree) |
| `/diary` or `/journal` (`/ndiary`, `/njournal` in its own window) | Journal: opens on a new, empty entry (the date and time of the day); the previous entries stay hidden unless **Previous entries** is turned on. The entry is written in Markdown on the left, rendered live on the right. Toolbar and shortcuts (Ctrl on Windows / Linux, ⌘ on macOS): **H1** (`# `, ⌘1) and **H2** (`## `, ⌘2), **B** bold (`**…**`, ⌘B), *I* italic (`*…*`, ⌘I), <u>U</u> underline (`<u>…</u>`, ⌘U), **</>** code (`` `…` `` inline, a ```` ``` ```` block for several lines, ⌘E), **🔗 Link** (`[text](https://…)` with the address selected, ⌘K; clicked in the preview it opens the browser, or the file for a local path), **🖼 Image** (picks pictures in the Pictures folder of `pictures.directory` and inserts `![name|480](/local/path)`, the path between `< >` when it has spaces; JPEG, PNG, GIF, WebP, BMP, and HEIC / TIFF on macOS), **• List** and **❝ Quote**. ## Windows

- **Main** — conversation, model picker, system prompt, ticker band, export buttons, status (Ollama + server)
- **Code** — extracted fenced code blocks (copy / save as)
- **Cache** — search, create, clone, edit, save (`PUT` / `POST /cache/update`)
- **Symbolic patterns** — same pattern for `/symbolicpattern` APIs (`Tags`, `isDeleted`, regex, symbol, event)
- **Ontology** — 1920x1080 window centered on the largest screen (clamped to its working area). Tree of all nodes (`POST /ontology/last`, `*`, up to 10,000) built from `nodeparentId`, with a node editor. Right-click a node to **Edit**, **Add child node**, **Attach to another node…** (then click the node to add as a *virtual parent*, Esc to cancel: its id is stored in `nodevirtualeftchildrenId` and the node, with all its children, is also shown under that parent, marked ⇢ linked and in italics; refused for itself, its real parent, an existing virtual parent, one of its descendants, or a more confidential parent), **Detach from "…"** on a linked occurrence, **Export…** (the node and its live descendants to a JSON file, without `id`/`nodeparentId`: the hierarchy is kept by nesting in `children`), **Import…** (creates the nodes of such a file under this node with new ids, via `PUT /ontology`), **Delete** (sets `isDeleted = true` on the node and its descendants, after confirmation), **Undelete** (sets `isDeleted = false` on the node and its deleted ancestors) or **Undelete with descendants**; the menu also toggles **Show deleted nodes**. A **Confidentiality** drop-down offers PUBLIC(PU), RESTRICTED(NR), SECRET(NS), COSMIC TOP SECRET(CTS), always in upper case (new nodes default to PUBLIC(PU)); former values are shown as their equivalent (Public → PUBLIC(PU), External/InternalRestricted → RESTRICTED(NR), Secret → SECRET(NS), TopSecret → COSMIC TOP SECRET(CTS)), any other stored value is kept in upper case. Levels go from the lowest to the highest (PUBLIC(PU) = 1 … COSMIC TOP SECRET(CTS) = 4, sent as `confidentialityLevel`, always consistent with `confidentiality`) and a child is never less confidential than its parent: a new child starts at its parent's level, a lower choice is refused (the editor shows the minimum) and saving below it is blocked, raising a node raises its lower descendants after confirmation, and imported nodes are raised to the level of the node they are imported under. The **Auto** button next to the name asks the Ollama model selected in the chat window (`POST /api/chat`, JSON-schema output) to fill the description, comment, emotion levels (Angry, Sad, Happy, Fear, Surprise, Disgust on a 0-10 scale), synonyms, tags (capitalised hashtags, always in English, e.g. `#DomesticPet`), 3 example sentences using the name, related entities and, when the node has none, the entity type (a type missing from the list is created in upper case, e.g. `MEDICAL_DEVICE`, and added to the drop-down for the session; config.yml is not changed); fields are filled but not saved (Save or Discard changes). Selecting a node refreshes it with `GET /ontology/{id}`; **Save** (Ctrl+S) uses `PUT /ontology` for new nodes and `POST /ontology/update` otherwise. Search combines `POST /ontology/search` (description) with a local match on name, symbol, type, synonyms and tags, and keeps the ancestors of hits visible. ## Main window

### Placement

On startup the window opens on the largest screen (by pixel area), docked to its right edge, at the full height of the screen's working area (taskbar excluded). Width stays at 900. The chat window is always on top, cannot be resized or maximized and cannot be moved (a move is undone). Every other window (tool windows, dialogs) is kept clear of it: when it overlaps the chat it is pushed to the free side of the screen and narrowed if needed; windows on other screens are not constrained.

The chat is also a Windows AppBar: its strip is removed from the working area of every application, so maximized windows stop at its left edge, and the windows of other applications moved over it (or full screen) are put back to its left.

### HTML code in the browser

When an answer contains an HTML page (an `html` / `htm` code block, or an untagged one starting with `<!doctype html>` or `<html>`), it is also opened in the default web browser, next to the code window: each block is written to the temporary folder (`kaonomi-html/answer-<date>-<time>.html`) and opened with the default application of `.html` files. Not during a prompt collection.

### Full chat (vertical screen)

When a vertical screen (taller than wide) is connected, a second window, **Kaonomi Full Chat**, opens with the chat and fills that screen's working area (another screen than the docked chat's when there is a choice; nothing opens when no screen is vertical). It is a clone of the chat sharing the same conversation, model, input and ticker: the Kaonomi band (3D face and clock) is at the top and takes 60 % of the height, with the header, ticker, conversation, input and status bar below. While the full chat is open, the docked chat is hidden (its strip of the screen is given back to the other applications): the systray icon and its commands bring the full chat to the front instead. Closing the full chat brings the docked chat back, with its Kaonomi band. Tool windows, the systray and `/bye` still belong to the docked chat.

`/fullchat` (also in the systray menu) opens the full chat in one of the work zones of the free space next to the docked chat: the left column of the zones (1 of 2 on an ultrawide screen, 1 of 3 on a super ultrawide one or when a vertical screen is connected, the left half on a smaller screen), at full height. The workspace is rebuilt in the other zones (its tools keep their state) and the docked chat stays open. Closing the full chat gives the zone back to the workspace.

When a screen is unplugged or plugged back, the display of the chat is reset a second later on the screens connected then: the chat is docked again on the largest one (widest ratio), the full chat opens again (on a vertical screen if there is one, else in its zone when it was docked in one, closed otherwise) and the workspace takes the free space next to the chat again, with the panes of that screen (its tools keep their state, each one in the pane of the same number when there is one).

### Workspace on a 4K screen

The tools opened as tabs (`/cache`, `/config`, `/calculator`…) share the workspace window, which fills the free space next to the docked chat (the whole working area of that screen while the docked chat is hidden). The chat is always docked on the largest screen (the widest ratio, so an ultrawide screen comes first, then the most pixels), and the workspace always opens next to it. When that screen is 4K or more (3840 × 2160, landscape or portrait), the workspace is split into **4 equal panes** (2 × 2), each with its own tabs: a new tool opens in the first empty pane (an empty pane reads "Free pane · the next tool opens here"), then in the pane with the fewest tabs; the views scroll when a pane is smaller than they need. A tool moves to another pane by dragging its tab there (the pane under the pointer is highlighted, the tool keeps its state) or with the **Move to the … pane** items of the right-click menu of its tab. The pane of each tool and the selected tab of each pane are kept in `screens.yml` (written by `/bye` and a moment after the tabs change: opened, closed, moved or selected), so the tools reopen in their panes at the next start; the calculator and the idea window are now reopened too. The panes start equal; the bars between them resize them horizontally (left / right) and vertically (top / bottom), highlighted when hovered, each pane keeping at least 240 × 160; a double-click on a bar makes the panes equal again. The sizes are kept in `screens.yml` too (`columnShares`, `rowShares`: share of the width of each column and of the height of each row of panes; the `splitX` / `splitY` of older files are still read). When that screen is ultrawide (3440 × 1440 or more, 21:9 or wider), the workspace is split the same way into columns side by side, separated by vertical bars: **3 columns** when the chat is in full size on a vertical screen (the docked chat is hidden, so the workspace has the whole width), **2 columns** otherwise (next to the docked chat). A super ultrawide screen (5120 × 1440 or more, 32:9 or wider) always gets **3 columns**. On smaller screens the workspace keeps a single tab strip. `/n…` commands still open a tool in its own window.

### Systray

The chat lives in the notification area (Kaonomi logo, not in the taskbar). A click on the icon shows or hides the chat; the close button hides it there too (the strip of the screen is given back while hidden). The icon menu gives access to every command: `/system`, `/log`, `/token`, `/cache`, `/json`, `/symbol`, `/ontology`, `/getthemes`, `/help`, `/theme:<name>` (sub-menu with every theme) and `/quit`; a command shows the chat and runs there as if typed. The application ends with `/quit`, `/bye` or `/exit`.

### Ticker band

A stock-market style band scrolls right to left above the conversation.

- Source: `POST /messageflow/last` with `{ "size": 100, "term": "*" }`, loaded at startup and refreshed every minute (15 s timeout).
- `color` = `red` → red text with ▼; `green` → green text with ▲; anything else → white.
- Hovering pauses the scroll. Clicking a message whose `url` is an absolute `http(s)` link opens it in the default browser (hand cursor and underline on hover).
- The band is hidden while no message is available; a failed refresh keeps the previous messages.

### Saved prompts

Above the input box, **Save prompt** writes the prompt being typed to a `.prompt.json` file (`{"prompt": "…"}`, the same format as the prompt collections) of the `prompts.directory` folder (the suggested name is made of its first words), and **Load prompt** puts the prompt of a `.prompt.json` file (former `.txt` / `.md` prompts are still read as plain text) in the input box (it replaces the text being typed) and, when `prompts.directprompt` is `true`, sends it right away, as if Enter had been pressed (with `false` / `off` it waits for Enter); when it cannot be sent at that moment (an answer is still coming, no model selected), it stays in the input box. The folder is created when needed.

**Prompt collection** runs a whole folder of prompts: pick a folder, a confirmation shows the number of `*.prompt.json` files found, then each prompt is sent in the chat one after the other, in file name order, each one waiting for the previous answer; the answers are shown at once, without the simulated streaming. **Esc** stops the run (the prompt being answered is cancelled too). A `.prompt.json` file holds `{"prompt": "…"}` (`content` or `text` are accepted too, and so is a plain JSON string); files without a prompt are skipped.

Each run writes its results in a child folder of the collection named from the date and the model, e.g. `test1\20261009-151724-gpt-oss-20b\`:

- one `NNN-name.completion.json` per prompt: index, prompt file, prompt, its number of words, completion, model, date, duration, stats, error flag;
- `name.rapport.json`: collection, model, language, start and end date, execution time, machine, user, number of prompts (in the collection, sent, skipped), whether it was stopped, total number of words of the prompts (parts separated by spaces), a summary of the topics of all the prompts with the number of prompts per topic (asked directly to the selected Ollama model; not generated when the run is stopped with Esc), and the full list of the prompts, each with the name (without folder) of its `.completion.json` file (the completions themselves are only in those files);
- `name.rapport.docx`: the Word document generated from `name.rapport.json` (the prompts with the name of their completion file).

When the collection folder name ends with `-FR`, `-EN`, `-DE` or `-NL` (e.g. `test1-FR`), a `"language"` field with that code is added to every `.completion.json` file and to the report (shown in the Word document too). With a language, each prompt and its completion are also saved on the Kaonomi server with `PUT /completion` (`prompt`, `completion`, `rawCompletion` = the completion without its text formatting (Markdown headings, bold / italic, code fences, links, bullets, tables, quotes and HTML tags removed; words, code and numbers kept), `model`, `language`, `topic` = the `"topic"` field of the `.prompt.json` file when it has one, `collectionName` = the folder name, `metadatas`: prompt file, index, number of words, duration, and `wordCounts`: every term of the prompt (`storedIn` = `PROMPT`) and of the completion without formatting (`COMPLETION`) with its number of occurrences; terms are compared in lower case, hyphenated words stay whole, apostrophes separate words, numbers count as terms); failed answers are not sent, and a server error never stops the run (the status line and the activity log give the number saved / failed). Without a language, nothing is sent.

### Export

Two buttons in the status bar (enabled once the conversation has messages) open a save dialog:

| Button | Output |
| --- | --- |
| **Export JSON** | `kaonomi-chat-<timestamp>.json`: export date, model, server URL, system prompt, and each message (`role`, `author`, `timestamp`, `content`, `stats`, `isError`) |
| **Export Word** | `kaonomi-chat-<timestamp>.docx`: title, the same header info, then each message with colored author, time, text and stats. Fenced code blocks use Consolas on a grey background; other Markdown is kept as plain text |

Answers still pending are not exported. The result (or error) is shown in the status bar.

## Anonymous notes

Every window (chat, cache, symbolic patterns, JSON client, code, ontology) has an **Add a note** icon in its header. It opens a popup with a red "All notes are anonyms!" banner and a text box; **Save** sends the note to `PUT /whitenote` (`text`, `context`, `appName`, `isDeleted`), then the popup closes after 2 seconds (on an error it stays open so the note can be sent again).

`context` is JSON text: the window name and the data being worked on (chat: model, theme, last 10 messages; cache / symbolic patterns: search term and selected document; JSON client: request and response; code: selected snippet; ontology: search, selected node with its path). No user name, machine name, date or id is sent, `userName` / `machineName` fields are removed from the context, long texts are truncated, and notes are not written to the activity log (log entries carry the user name and time). The popup shows the context before sending.

## Activity log

Every user action and its outcome is logged to the Kaonomi server with `PUT /log` (`appName`, `id`, `date`, `machineName`, `userName`, `comment`, `type`), type `INFO` (success, plain event) or `ERROR` (failure) only. The comment reads `Area | action: details` (areas: App, Chat, Prompt, Ticker, Export, Evaluation, Code, Cache, Symbol, JSON client, Ontology, System); prompts and answers are truncated to 200 characters.

Logged: application start / close, Ollama model list and model choice, every command, prompts and answers (model, tokens, duration), errors, new conversation, copy, exports, like / dislike, ticker load / failure / link opened, code copy / save, cache and symbolic pattern searches and saves, JSON client requests, ontology load, search, add, save, discard, delete, undelete, export, import and Auto fill. Progress messages are not logged; the ticker (refreshed every minute) only logs changes between success and failure.

Logs are queued and sent in the background, one by one: they never slow the UI nor show errors. When the server is unreachable they are dropped (written to the debug output only). On exit, the application waits at most 3 seconds for the last entries.
